# Use SvelteKit loads for confirmed renderer data

SvelteKit universal loads own confirmed renderer data, including saved views, in the static Electron SPA. Explicit desktop-read dependencies and targeted invalidation replace ADR-0005's mutable controller snapshot and mount initialization. A small Svelte command coordinator owns synchronous admission, operation progress, and contextual outcomes through the required refresh, not another data cache. This follows [issue #163](https://github.com/Cahllagerfeld/tuxedo-app/issues/163).

Reads and activation are separate: loading or preloading a Workspace cannot persist its selection, retarget observation, clear Undo, or advance an existing mutation revision. Only actual admitted navigation activates the destination; the reader is actionable only when the route and backend confirmation agree. Startup resumes an available remembered Workspace with history replacement. Home is reserved for setup and recovery; a plain visit resumes an available Active workspace, and the toolbar exposes no Home navigation.

The root universal load returns the shared session and saved views. The Workspace detail page's load reads its requested destination and declares its own invalidation dependencies. SvelteKit waits for the applicable loads before updating the view. Components use generated `LayoutProps` and `PageProps`; context shares getters and commands without copying their results. `AppState` is removed. Reader state contains local controls and selection, with file summaries and persisted preferences derived from the load getter.

The client initialization hook restores the backend and activates an explicit startup destination; startup command failures become load-owned recovery data. The launch page at `/` redirects from its load to an available remembered Workspace, or to the picker at `/workspaces`, before rendering. The detail loader checks its repeatable read against the parent confirmation and redirects failures to Home before rendering. Home's loader uses the failed Workspace ID in the URL to read its explanation, without a mutable snapshot or a load side effect. The user can retry refreshing the session, reopen its saved row, or choose another Workspace. The separate recovery component and its focus-transfer effect are removed; SvelteKit owns navigation focus and the startup redirect.

Navigation admission covers activation and the destination load, including native history traversal. A refresh admits its exact Home recovery URL while retaining admission until the redirect finishes. A redirected history destination uses SvelteKit's shallow replacement API to keep the address aligned with Home without changing history-entry identity. The shared session load tracks the destination pathname so a history traversal reads the newly activated backend confirmation. A per-Workspace dependency discards speculative destination data after activation while preserving the outgoing reader. Observation resumes after navigation completes. Explicit refresh completion reconciles local filter choices without a state-synchronizing effect.

Commands retain the backend's confirmed outcomes and consistency checks, then invalidate affected reads instead of patching renderer snapshots. Admission remains closed through refresh; a committed write followed by a failed read is reported as saved with a refresh failure, never retried as a write. External Todo-file events use the authoritative backend refresh and targeted invalidation. Drafts, dialogs, filters, focus, and selection retain their existing local ownership and Workspace-change reset rules.

Filesystem access, catalogue persistence, parsing, serialization, scoped identities, revisions, targeted-content checks, observation resources, and atomic writes remain backend responsibilities under ADR-0004 and ADR-0006. Persisted formats and supported todo.txt cases are unchanged.
