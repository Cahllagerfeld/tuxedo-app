# Use TanStack Query for desktop RPCs

TanStack Query owns confirmed renderer data and the request lifecycle of typed, Promise-based desktop RPCs. SvelteKit universal loads ensure queries through the shared QueryClient before rendering; components subscribe to that same cache, following TanStack's [Using query](https://tanstack.com/query/latest/docs/framework/svelte/ssr#using-query) load-prefetching pattern. This supersedes ADR-0007's load-owned snapshots: loading and mutation invalidation should use the same definitions without a broad command object also serving as the reader's data interface.

The shell session query owns the backend's coherent confirmation of the Workspace catalogue, Active workspace, scope, revision, and Undo. Workspace-keyed destination queries call the repeatable `readWorkspace(id)` RPC for their Workspace and Todo file. An Active workspace read reuses its backend-confirmed file instead of independently parsing disk or comparing JSON snapshots. An inactive Workspace read parses its file without changing persistence, revision, Undo, or observation, so hover preloading can fill the destination cache before activation. The same read-only behavior applies before startup restoration. Separate destination entries keep the outgoing reader visible while navigation activates the next Workspace. A separate query owns saved views. Read projections derive from query data; loads and commands keep no second mutable snapshot. IPC queries use `networkMode: "always"` because desktop access does not depend on network connectivity.

Feature-local query-key factories order keys from broad to specific: Workspace, then session, views, or destination, then destination ID. This allows intentional family invalidation without string duplication, following [Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys).

Mutations await affected session and destination invalidation after successful writes and conflicts. A small command coordinator synchronously admits operations through refresh, because observer notifications alone cannot prevent two same-turn commands. It owns operation context and recovery, while Query owns request lifecycle. Confirmed contents stay visible during refresh, and a saved write followed by a failed refresh reports that distinction without retrying the write. Mutations use `networkMode: "always"` and disable retries. External Todo-file events first restore authoritative backend state, then invalidate the affected queries.

Actual admitted navigation remains the only activation path: queries, loads, preloads, and invalidation cannot persist selection, retarget observation, clear Undo, or advance an existing mutation revision. Displayed Workspace identity follows the route; mutation controls require that route identity to match the confirmed backend Active workspace. Startup restoration, remembered-Workspace redirects, Home recovery, history navigation, and the outgoing confirmed reader retain ADR-0007's behavior. Drafts, dialogs, filters, focus, and selection stay local Svelte state.

The earlier Query integration manually merged mutation responses into a controller-shaped query owner and disabled automatic revalidation. This integration replaces that response-merging machinery with repeatable reads and awaited invalidation. Backend scope, revision, targeted-content checks, serialization, atomic writes, and Effect runtime ownership remain unchanged under ADR-0004 and ADR-0006. Persisted formats and supported todo.txt cases are unchanged.
