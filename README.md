# Tuxedo

Tuxedo is a macOS Electron desktop application with a SvelteKit SPA. It organizes plain-text Todo files into saved Workspaces and supports Todo-item creation, editing, completion, uncompletion, reordering, and precise deletion.

Choose **New workspace** to create an empty Todo file or open an existing one, then choose a Workspace name and color. Creation uses the native Save dialog with `todo.txt` suggested; both choices support other filenames such as `work.txt`. The selected location is shown before submission. Cancelling setup leaves the file and Workspace catalogue unchanged. After setup, **Add your first Todo item** opens the editor; instructions and examples stay out of your file.

Setup validates Workspace names and canonical file references before creating a file. A Save selection authorizes creation or the native dialog’s confirmed replacement; opening an existing file never rewrites it. If a file changes after Save selection, select it again before replacing it. If the file is saved but catalogue persistence fails, setup reports the saved location and retains the form: submitting again connects that file without rewriting it, preserving later edits. A committed setup awaiting a screen refresh uses read-only recovery.

## Development

Install dependencies with `devenv shell -- pnpm install --frozen-lockfile`, then launch with `devenv shell -- pnpm dev`. Vite and vite-plugin-electron build/watch main and preload and serve the renderer at `http://127.0.0.1:1420`; Ctrl-C stops the application. Renderer updates use Vite HMR.

SvelteKit 3 uses native `#lib/*` package imports with explicit file extensions. Its renderer configuration lives in `apps/desktop/vite.config.ts`, and `svelte-kit sync` generates the `$app/tsconfig` base. Keep TypeScript on the shared 6.x version until SvelteKit and svelte-check support 7.x.

The private pnpm workspace contains the Electron host and renderer in `apps/desktop` (`@tuxedo/desktop`), Effect-native domain services in `packages/backend` (`@tuxedo/backend`), and browser-safe TypeScript contracts in `packages/contracts` (`@tuxedo/contracts`), with one root lockfile. Renderer, preload, main, backend, and forms consume the contracts through explicit source exports. Root commands use Turborepo to coordinate package-local scripts; formatting also covers root documentation, scripts, and configuration. Backend and contracts can each be checked and tested independently with `pnpm --filter @tuxedo/backend check` / `test` and `pnpm --filter @tuxedo/contracts check` / `test`, without SvelteKit or Electron startup.

Desktop constructs one managed Effect runtime and owns admission, the Promise bridge, native watchers, platform resources, and shutdown. The backend exports a Workspace session service and scoped Layer with injected filesystem, identity/date, and observation capabilities; it owns parsing, JSON catalogue persistence, atomic replacement, and operation serialization. The isolated preload exposes a runtime-validated typed desktop API. SvelteKit route data owns catalogue, Todo-file/preferences, and independent saved-view resources. A command coordinator tracks admission and confirmation receipts through targeted route publication; counts and facets derive directly from the route-owned Todo file.

`readWorkspaceCatalogue({})` and `readWorkspace({ workspaceId })` are repeatable, validated IPC reads, separate from the serialized `switchWorkspace` activation command and startup restoration. They read disk without initializing or accepting a session, persisting selection, advancing revisions, changing Undo, or acquiring/retargeting observation. A missing catalogue yields an empty catalogue without creating it; corrupt/unreadable catalogues and unknown/missing/unreadable destinations return explicit rejected results and preserve the current session and files. Reads share the backend semaphore for coherent confirmation metadata and are admitted/drained by the application runtime during shutdown; they reserve no renderer command/navigation gate and acquire no persistent resources.

Catalogue reads return the remembered catalogue selection separately from nullable authoritative `selection` metadata (null before initialization). Destination reads return the requested Workspace and its Todo file with `provenance.status: "speculative"`, or `"confirmed"` plus a selection receipt only when Workspace/path, persisted selection, preferences and exact file contents still match authoritative acceptance. A receipt identifies scope, revision, Workspace, Todo-file path and optional Undo label; it contains no loaded snapshot. Speculative data cannot authorize mutations. Consumers must match destination identity and confirmation scope/revision against the actual activation or command result, rejecting late reads. Changed disk contents remain speculative until an explicit authoritative refresh accepts them; observation currently signals before that acceptance, so a future route owner must refresh authoritatively before invalidating its reads. The current controller and existing lifecycle APIs retain their behavior until the coordinated route cutover in #180; saved-view read ownership is separate.

The Todo-file summary provides total, open, completed, and skipped-line counts. Filter facets and their counts derive from the selected completion view of the confirmed Todo file.

The shared Todo-item editor supports Description, Priority, Creation date, Projects, Contexts, and `key:value` metadata; completed items also expose their Completion date. Completion records the local date and stores Priority as `pri:A` metadata; uncompletion restores a valid single-letter Priority. The parser also accepts legacy completed items with a leading Priority or no Completion date.

Configure recurrence in Metadata with `rec:1d`, `rec:2w`, `rec:1m`, or `rec:1y` (positive whole-number days, weeks, months, or years; the last `rec:` token wins). Checkbox completion and the editor's Completed control generate one open successor immediately after the original. Its Due date is relative to the recorded Completion date, month/year intervals clamp to month-end, and its Creation date is local today. Unsupported rules such as `rec:+1w` complete normally with a notice. Date overflow rejects the whole change. Completed-history edits and already-completed creation generate nothing.

Generation adds app-owned `tuxedo-generated:1` metadata to the original and excludes it from the successor. Any existing value of that key prevents regeneration. Tuxedo retains it through reopening and editing, even if removed from an editor draft; external tools must retain it for duplicate protection. Reopening the original leaves its successor alone, and deleting the successor does not reset the marker. One Undo last change restores the exact file before completion, marker insertion, and successor creation. When the source has valid effective Due and Show from dates, the successor's Show from keeps the same signed calendar-day lead time relative to its new Due date; with a valid Show from but no valid Due date, absolute Show from dates are omitted from the successor while malformed or unsupported `t:` tokens are copied unchanged. A calculated Show from outside the supported date range rejects the whole completion with no write. Structured Repeat controls and bulk recurrence remain separate features.

Creation checks the whole Todo file against confirmed contents; editing checks its targeted physical line, preserving external changes elsewhere. An omitted Creation date uses the current local calendar date; an explicit date or no date is preserved.

Drag the row handle to reorder the displayed Todo items within their existing physical-line positions. Hidden Todo items, blank lines, skipped lines, and each position's line ending remain in place. External edits reload the Active workspace's Todo file while the Workspace session is idle. Changed parsed contents show an info notice; a stably unreadable file enters the Empty state with a warning. Mutations check disk contents before writing and return confirmed data or a conflict.

Metadata is stored in Electron's application-data directory as `workspaces.json`. The rewrite begins with a fresh JSON catalogue; existing legacy metadata and external Todo files are preserved. Catalogue-only Workspace deletion never deletes a Todo file. Setting `TUXEDO_USER_DATA` to a temporary directory isolates development/integration data.

## Task orchestration and local cache

Use root commands through `devenv shell -- pnpm <command>`. `check` orders contracts → backend → desktop checks. `test:backend` discovers all three projects; `test:unit` runs the desktop renderer suites. `lint` runs Oxlint over JavaScript/TypeScript across the repository, ESLint with TypeScript and Svelte recommended rules over desktop `.svelte` files (scripts and templates), and Prettier over the entire repository, including documentation, scripts, workflow, and environment configuration. Oxlint excludes `.svelte` files so each file has one linter; `.svelte.ts` files use Oxlint. Generated outputs and reference checkouts are excluded. `lint:fix` applies automatic lint fixes; `format` writes formatting across the repository. Run individual linters with `pnpm lint:oxlint` or `pnpm --filter @tuxedo/desktop lint:svelte`. The existing independent backend/contracts `check` and `test` commands remain available.

Backend and contracts export TypeScript source and have no build task. Turbo's scriptless `source` task follows their actual workspace dependencies, so their source and configuration hashes invalidate dependent desktop builds and tests without producing synthetic library artifacts. `build` restores `apps/desktop/build`, `dist-electron`, and the complete `.svelte-kit` directory. Source inputs include tracked package files, ignored `.env*` files at root and desktop, workspace/lockfile configuration, and the root environment/tooling configuration. Build environment inputs include `NODE_ENV`, `NODE_OPTIONS`, `VITEST`, `VITE_*`, `PUBLIC_*`, CI, timezone, and locale. Add any future output-affecting environment variables to `turbo.json` when introducing them.

Only builds are cached, with a strict environment allowlist. Uncached tasks retain the caller environment (including custom Playwright paths and native test settings). Checks, formatting checks, unit/backend tests, real Electron workflows, Forge packaging, and copied-package verification always execute. Development, preview, and watch tasks remain persistent and uncached. Native tasks depend on the build through Turbo; package-local native scripts perform only their own responsibility, so use the root entry points to obtain prerequisites. `test:package` always packages again before testing a copy outside the checkout. Run native commands with `devenv shell -- env -u ELECTRON_RUN_AS_NODE pnpm test:electron` (or `test:package`, `test:electron:dev`, `package:macos`, `dev`). Avoid running native suites together: development uses fixed port 1420 and the native suites control their own isolated application.

The root `scripts/turbo.mjs` launcher fixes the working directory, restricts Turbo to local cache reads/writes, forwards termination signals, and hashes the checkout path, OS release, architecture, and exact Node version. Absolute SvelteKit generated paths and host-dependent tooling must not be reused across those environments. Use `pnpm turbo run <task>` for diagnostics/custom task combinations so this context is preserved. Remote caching is disabled; no cache account, CI artifact cache, or service is configured. `.turbo` directories contain disposable local cache/logs and are ignored by Git and Prettier.

To inspect task prerequisites, run `devenv shell -- pnpm turbo run build --dry=json`. To verify restoration, run a cold `pnpm build`, repeat it for a cache hit, delete the three generated directories listed above, and build again. Changing backend/contracts source or build configuration must cause a cache miss; repeated native commands must show their scripts executing even when the build is restored.

## Verification

Run these commands through `devenv shell --` (under T3, use `devenv shell -- env -u ELECTRON_RUN_AS_NODE pnpm ...` for Electron and package commands): `pnpm check`, `pnpm test:unit`, `pnpm test:backend`, `pnpm lint`, `pnpm build`, and `pnpm test:electron`. `check` covers Svelte/renderer types, backend/main/preload/contract types, and import restrictions. Unit tests include Chromium renderer behavior; install its browser with `pnpm --filter @tuxedo/desktop exec playwright install chromium` when needed. Backend tests use real temporary files and scoped Effect Layers. Desktop Promise bridge tests retain todo.txt fixtures in `apps/desktop/electron/session-tests/fixtures`, resolved relative to their test module.

`pnpm build` produces the static SPA in `apps/desktop/build` and desktop bundles in `apps/desktop/dist-electron`. `pnpm test:electron` builds and launches real Electron to exercise production protocol loading, trusted preload/IPC, runtime input validation, Workspace lifecycle, completion, conflicts, and deletion with temporary data. `pnpm test:electron:dev` runs the same workflow suite against the development renderer using its `--dev` option. macOS CI runs types, formatting, browser/backend tests, production build, and real Electron integration. `pnpm test:package` builds an unsigned Forge macOS app and launches its actual executable to repeat the same workflow suite, verify bundled assets, route fallback/reload, and reject protocol traversal. Development renderer origin configuration is ignored in packaged apps. Signed distribution, automatic updates, and Windows/Linux verification are deferred.

Electron integration and package tests keep windows hidden by default. Run `devenv shell -- pnpm test:electron:visible` to show the app and check that it opens maximized with native fullscreen off. Development and package tests also accept `--visible`: `devenv shell -- pnpm test:electron:dev --visible` or `devenv shell -- pnpm test:package --visible`. Hidden tests still use real Electron and exercise the renderer and preload/IPC; only visible mode checks maximization. Normal app launches are unchanged.

The bow-tie application icon lives in `apps/desktop/assets/icon.png`; `apps/desktop/assets/icon.icns` contains the macOS sizes used for packaging. The renderer uses `apps/desktop/static/favicon.png`. Unpackaged macOS launches also set the Dock icon from the PNG. The artwork fills the image without transparent padding.

## Local macOS application

Run `devenv shell -- pnpm package:macos` on macOS. Forge packages the bundled ESM main/backend, sandboxed CommonJS preload, static SPA, and package metadata from a temporary allowlisted directory. Runtime dependencies are bundled; repository sources, tests, build tools, and pnpm's symlinked dependency tree are excluded. The resulting unsigned application is `apps/desktop/out/Tuxedo-darwin-<host arch>/Tuxedo.app`. Launch it with `open apps/desktop/out/Tuxedo-darwin-arm64/Tuxedo.app`, or run `Contents/MacOS/Tuxedo` with a temporary `TUXEDO_USER_DATA` directory for isolated checks.

`devenv shell -- pnpm test:package` is the repeatable package verification command and runs in macOS CI. It copies the app outside the checkout and clears Node resolution overrides to verify operation without development dependencies. It verifies actual executable loading, security preferences and preload validation, JS/CSS/font assets, route reload, traversal rejection, new-file Workspace setup, process-restart restoration, completion and Undo using disposable data. The Electron workflow also covers setup cancellation, adding the first Todo item, opening an unchanged `work.txt`, and adding another Workspace. Native Save/Open dialogs must also be checked manually in the packaged app: verify the suggested `todo.txt`, another filename and directory, ordinary existing-file replacement prompts, and cancellation. Controlled native-dialog results in automated workflows do not test the operating system’s actual dialogs.

Local package checks were performed on macOS 26.6.2 arm64 with Node 24.20.0. This is local unsigned delivery; Windows/Linux, signing, notarization, installers, and public distribution are unverified.
